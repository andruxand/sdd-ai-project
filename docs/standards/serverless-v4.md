# Serverless Framework v4 Standards

## Configuration (`serverless.ts`)

- `frameworkVersion: '4'` — enforce v4.
- `stage: '${opt:stage, "dev"}'` — always explicit, never hardcoded.
- `region: 'us-east-1'` — set explicitly, override per environment.
- `runtime: 'nodejs22.x'` — use latest LTS.
- `logRetentionInDays: 30` — at provider level.

## Local development with serverless-offline

Use `serverless-offline` to run the API Gateway + Lambda stack locally without
deploying to AWS. This is mandatory for local development — never test handlers
only via unit tests when integration behavior matters.

### Setup in `serverless.ts`

```typescript
const serverlessConfiguration: AWS = {
  service: 'your-service',
  frameworkVersion: '4',
  plugins: ['serverless-offline'], // must be first plugin
  provider: {
    /* ... */
  },
  custom: {
    'serverless-offline': {
      httpPort: 3000, // API Gateway local port
      lambdaPort: 3002, // direct Lambda invocation port
      noPrependStageInUrl: true, // /endpoint instead of /dev/endpoint
      reloadHandler: true, // hot reload on handler file changes
    },
  },
  functions: {
    /* ... */
  },
};
```

### Available scripts (from `services/api`)

| Script                 | Command                                     | Purpose                            |
| ---------------------- | ------------------------------------------- | ---------------------------------- |
| `npm run dev`          | `serverless offline start`                  | Start local API on port 3000       |
| `npm run dev:watch`    | `serverless offline start --reloadHandler`  | Same + auto-reload on code changes |
| `npm run invoke:local` | `serverless invoke local --function <name>` | Test a handler directly, no HTTP   |
| `npm run sls:print`    | `serverless print`                          | Inspect resolved config            |
| `npm run sls:package`  | `serverless package`                        | Preview deployment artifact (ZIP)  |

### Local workflow

```bash
# Terminal 1 — API
cd services/api && npm run dev

# Terminal 2 — Frontend (proxies /api → localhost:3000 automatically)
cd apps/web && npm run dev

# Or from the monorepo root:
npm run dev     # starts both in parallel via Turborepo
npm run dev:api # backend only
npm run dev:web # frontend only
```

### Anti-patterns for serverless-offline

- **Do NOT** use `serverless-offline` as a substitute for writing unit tests —
  use it alongside them for integration paths.
- **Do NOT** configure `httpPort` differently per developer — keep it at 3000 so
  the Vite proxy config (`/api → :3000`) works consistently for everyone.
- **Do NOT** commit `serverless-offline` to `plugins` without the `devDependency`
  in `services/api/package.json` — it will break production deployments that run
  `npm ci --omit=dev`.

> `serverless-offline` is a `devDependency`. It is automatically excluded from
> the deployment package because Serverless Framework bundles only production deps.

## Per-function configuration

- Define `memorySize` and `timeout` explicitly per function.
- Define IAM `iamRoleStatements` at function level (not provider).
- Use `environment` at function level for function-specific vars.
- Use `events` to define HTTP, SQS, SNS, schedule triggers.

## Environment management

- Use `${ssm:/path/to/param}` for secrets and config per stage.
- Never hardcode stage, region, or account IDs in business logic.
- Use serverless variables for stage-dependent configuration.

## Infrastructure as Code validation

- `cfn-lint`: validate CloudFormation templates generated by SLS.
- `cfn-guard`: enforce organizational policies on templates.
- `checkov`: scan for security misconfigurations.
- All three run in CI on pull requests.

## Separation of concerns

- `serverless.ts`: infrastructure wiring only (functions, events, resources, IAM).
- `src/handlers/`: thin entry points that delegate to use cases.
- `src/usecases/` or `src/services/`: business logic.
- Never put business logic in `serverless.ts`.

## Packaging

- Use esbuild (via serverless-esbuild) or equivalent bundler.
- Exclude dev dependencies from deployment package.
- Keep packages small for faster cold starts.

## Anti-patterns

- Do NOT use `iamRoleStatements` at provider level with `*` resources.
- Do NOT deploy without stage parameter.
- Do NOT hardcode ARNs — use `!Ref`, `!GetAtt`, or SSM.
- Do NOT use `serverless.yml` — use `serverless.ts` for type safety.
- Do NOT leave `versionFunctions` at default (true) without `serverless-prune-plugin` — fills Lambda storage quota.
- Do NOT let Serverless create one deployment bucket per service — consolidate to a shared bucket per stage/region.
- Do NOT omit resource tags — cost allocation and incident triage require Project, Environment, Owner, CostCenter, Version.
- Do NOT bundle `@aws-sdk/*` — provided by Lambda runtime; bundling it adds ~10 MB per function with no benefit.

> For the full project-level configuration baseline (tags, deployment bucket, version management, packaging, naming, provider defaults), apply the `.github/skills/serverless-baseline` skill.

## Datadog Lambda integration

Use `serverless-plugin-datadog` to instrument Lambda functions. This plugin installs
the Datadog Lambda Extension Layer automatically — no manual layer ARN required.

```typescript
// serverless.ts
plugins: ['serverless-plugin-datadog'],

custom: {
  datadog: {
    apiKeySecretArn: '${ssm:/myapp/${opt:stage}/datadog/api-key-secret-arn}',
    site: 'datadoghq.com',
    env: '${opt:stage}',
    service: '${self:service}',  // must match project_name in openspec/config.yaml
    version: '${env:GIT_SHA, "local"}',  // set by CI from git SHA or semver tag
    enableDDTracing: true,
    captureLambdaPayload: false,  // never capture full payloads (PII risk)
    forwardErrorsToDatadog: true,
    logLevel: 'warn',
  },
},
```

### Rules

- **Never** set `DD_API_KEY` as a plain env var — always use `DD_API_KEY_SECRET_ARN`
  pointing to AWS Secrets Manager.
- `DD_ENV`, `DD_SERVICE`, and `DD_VERSION` are injected by the plugin from `custom.datadog`.
  Do not redeclare them in `environment`.
- `captureLambdaPayload: false` is mandatory — request/response bodies may contain PII.
- `DD_VERSION` should be the git SHA or semver tag injected by CI (`GIT_SHA` env var).
- Powertools Logger/Tracer/Metrics remain mandatory alongside Datadog.
  Powertools handles structured log formatting; Datadog collects and forwards them.

## Lambda runtime best practices

### Connection reuse (mandatory)

AWS SDK clients, HTTP clients, and DB connections MUST be initialized at module
level — outside the handler function. Lambda reuses the execution environment across
warm invocations; initializing inside the handler wastes latency on every call.

```typescript
// ✅ Correct — initialized once at module load
const dynamodb = new DynamoDBDocumentClient(
  new DynamoDBClient({
    maxAttempts: 3,
  }),
);
const httpClient = new HttpClient({ keepAlive: true });

export const handler = async (event: APIGatewayProxyEvent) => {
  // use dynamodb and httpClient here
};

// ❌ Wrong — initialized on every invocation
export const handler = async (event: APIGatewayProxyEvent) => {
  const dynamodb = new DynamoDBDocumentClient(new DynamoDBClient({})); // cold path every time
};
```

### Env var validation at startup (mandatory)

Required environment variables MUST be validated at module level, not inside the
handler. This causes failures at cold start (visible in logs and metrics) rather
than silently failing mid-request.

```typescript
// At top of handler file — before any exports
const TABLE_NAME = process.env.TABLE_NAME;
const QUEUE_URL = process.env.QUEUE_URL;

if (!TABLE_NAME || !QUEUE_URL) {
  throw new Error(
    `Missing required env vars: TABLE_NAME=${TABLE_NAME}, QUEUE_URL=${QUEUE_URL}`,
  );
}
```

> Use Zod or a small validation utility to consolidate env validation if there are
> more than 3 required vars.

## API versioning strategy

URL-based versioning (`/v1/`, `/v2/`) is mandatory for public or consumer-facing
APIs. Header-based versioning (`Accept: application/vnd.api+json;version=2`) is
allowed only for internal service-to-service APIs.

### Rules

- New endpoints start at `/v1/`. Increment only on breaking changes.
- A breaking change is: removing a field, changing a field type, changing a status
  code, removing an endpoint, or changing auth requirements.
- Additive changes (new optional fields, new endpoints) are NOT breaking — no version bump.
- Old versions must remain operational for a **deprecation period of 90 days** minimum.
  Document the deprecation date in the OpenAPI spec using the `deprecated: true` field.
- During deprecation: add a `Deprecation` response header with the sunset date.
- After sunset: return `410 Gone` with a message pointing to the new version.

### In serverless.ts

```typescript
functions: {
  getUserV1: {
    handler: 'src/handlers/users/get-v1.handler',
    events: [{ http: { path: '/v1/users/{id}', method: 'GET', ... } }],
  },
  getUserV2: {
    handler: 'src/handlers/users/get-v2.handler',
    events: [{ http: { path: '/v2/users/{id}', method: 'GET', ... } }],
  },
},
```

### In OpenAPI spec

```yaml
/v1/users/{id}:
  get:
    deprecated: true
    description: 'Deprecated. Use /v2/users/{id}. Sunset: 2026-10-01.'
```

## Checklist

- [ ] Stage and region explicit.
- [ ] `serverless-offline` configured in `plugins` and `custom` with `httpPort: 3000`.
- [ ] `npm run dev` starts local API via `serverless offline start`.
- [ ] Per-function memory, timeout, and IAM.
- [ ] Secrets via SSM/Secrets Manager.
- [ ] IaC validation in CI (cfn-lint, Guard, Checkov).
- [ ] Business logic separated from wiring.
- [ ] `serverless-plugin-datadog` configured (if Datadog observability pack enabled).
- [ ] `DD_API_KEY_SECRET_ARN` used — never plain `DD_API_KEY` env var.
- [ ] `captureLambdaPayload: false` set.
- [ ] AWS clients initialized at module level (not inside handler).
- [ ] Required env vars validated at module load time.
- [ ] DLQ defined for every async function trigger.
- [ ] Write operations wrapped with Powertools idempotency.
- [ ] API version strategy defined (URL-based for public APIs).
- [ ] Deprecated versions annotated in OpenAPI with sunset date.
